# Пилотный стенд Prodigy MAX

## Проверка восстановления, 27 сентября

Для всей связки использовать `capture-full-backup.sh` и
`run-full-restore-review.py`. Первый скрипт кратко останавливает только
приложения MAX, сохраняет обе базы, оригиналы Prodigy, файлы и индекс Vedomo,
настройки, идентификаторы образов и контрольные суммы. Возвращает приложения
в работу даже при ошибке. При незавершённой отправке или индексации не начинает.

На VPS запускать сохранённый LF-файл:

```sh
sh /opt/prodigy-max/capture-full-backup.sh </dev/null
```

Закрытые настройки остаются на сервере. Для локальной проверки перенести
только два `.dump`, два `.counts`, три `.tar.gz` и `SHA256SUMS` в закрытую
папку `full-stack-*`, исключённую из Git. После подготовки из START.md:

```sh
python deploy/max/run-full-restore-review.py --backup output/playwright/full-stack-vZb12xVa --project prodigy-max-review-restore-new
```

Нужны образы `prodigy-max:cold-check-20260927` и
`vedomo-backend:cold-check-20260927`, либо указать свои через
`--prodigy-image` и `--vedomo-image`. Используется существующий кеш BGE-M3,
только для чтения. Скрипт откажется запускаться поверх существующих ресурсов.
Рабочие токены, почта, worker и генерация AI в копии не используются.
Миграции, поиск по сохранённому индексу, точный источник и HTTPS-путь
сотрудника проверяются без повторной индексации. Том оригиналов в этой
копии пуст; непустой том и точные байты проверены отдельной репетицией ниже.

Успех обозначается `FULL_RESTORE_PASSED`. Проверочный проект останавливается,
бэкап и тома сохраняются. Не использовать `down -v` или глобальный prune.

### Предыдущая проверка оригиналов

`verify-restore.sh` восстанавливает согласованную копию PostgreSQL Prodigy
и том оригиналов в новые закрытые ресурсы. Не сбрасывает рабочую базу,
не удаляет тома. Проверяет количество записей, утверждённый источник и
точные байты файлов. Проверка прошла на копии `backups/restore-pair-fREDSy`.
Это историческая проверка конкретной версии образа, не команда обновления
текущего пилота. Полную связку проверяет новый helper выше.

Поместить helper и `scripts/max-restore-fixture.ts` в пути, указанные в скрипте.
Запускать сохранённый LF-файл, а не передавать его через stdin:

```sh
sh /opt/prodigy-max/verify-restore-20260927.sh --verify-backup /opt/prodigy-max/backups/restore-pair-fREDSy </dev/null
```

Без аргументов скрипт сначала создаёт свою проверочную запись и кратко
приостанавливает только web/worker пилота для согласованной копии.
При ошибке возвращает сервисы и удаляет только свою запись. При высокой
задержке диска отказывается начинать. Бэкап содержит закрытый `.env`;
не публиковать и не отправлять его вместе с исходниками.

При остановке worker сначала проверить код ошибки и очередь. `UNCERTAIN`
не возвращать в `PENDING` без проверки фактической доставки. После таймаута
базы восстановить обработчик можно вручную, когда база доступна и нет новой
неопределённой отправки. Автоматический restart loop намеренно выключен.

Адрес: `https://prodigy-max.45-139-78-17.sslip.io/max`. Сервер: `45.139.78.17`, папка `/opt/prodigy-max`, Compose project `prodigy-max-pilot`. Это технический пилот на общем сервере, не полный релиз LMS. Домен использует sslip.io и не требует покупки.

## Границы стенда

- У пилота собственные web, PostgreSQL, gateway, worker, сеть и volume. Остальные проекты и настройки общего proxy не менять.
- Публично открыты только Mini App и нужные ему MAX API. Обычные страницы LMS и административные маршруты закрыты gateway.
- Web ограничен 768 MiB и 0.7 CPU, БД - 384 MiB и 0.35 CPU. Для защищённых запросов к Vedomo web также подключён к egress-сети. Эти лимиты не заменяют наблюдение за общим сервером.
- В web установлено `MAX_DISABLE_EMAIL=true`. Worker работает отдельно; изменение его окружения требует отдельного обновления контейнера.

## Обновление

Собирать образ локально, не на общем VPS. Web: `prodigy-max:document-import-v2-20260927`; worker: `prodigy-max:onboarding-guide-20260927`. Выбрать `compose.yml`, `compose.chat-ux.yml`, `compose.knowledge-ui.yml`, `compose.chat-navigation.yml`, `compose.onboarding-guide.yml`, `compose.ui-integration.yml`, `compose.tester-ready.yml` и `compose.document-import.yml`. На сервере сначала проверить новый Compose через `docker compose config --quiet`, затем применить миграции и обновить только нужные сервисы. Не выполнять глобальные Docker prune, restart или `down -v`. На последнем обновлении пересоздан web, worker возобновлён на прежнем образе. Конфигурация собственного gateway перечитана без перезапуска; соседние проекты не менялись.

Gateway разрешает имя `web` через Docker DNS с обновлением каждые 5 секунд.
После изменения `nginx.conf` проверить его командой `nginx -t` в одноразовом
gateway-контейнере, сохранить старый файл и выполнить `nginx -s reload` только
в `prodigy-max-pilot-gateway-1`. Общий proxy не менять. Копия прежнего файла:
`backups/nginx-before-dns-20260926.conf`.

## До полного релиза

Нужны проверка HR-экрана с отдельного MAX-аккаунта, полная репетиция восстановления
и тест AI и скачивания на телефоне. Чистый запуск с настоящим GigaChat проверен
в отдельной копии. Настоящие документы сотрудников пока не подключать.
При зависшей отправке бота не возвращать очередь в `PENDING` без проверки
доставки: возможны дубли сообщений.

Корневой сертификат MAX монтируется только в worker через `max-ca.pem`. Не устанавливать его на весь сервер и не отключать проверку TLS. Источник: `https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt`; отпечаток нужно сверять при обновлении сертификата.
